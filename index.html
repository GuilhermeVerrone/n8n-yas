Serviço 02 · versão A

Catálogo

O que existe, quanto custa, e se dá pra vender agora — numa resposta só.

Visão geral

Se você vai integrar com este serviço, estas são as três coisas que precisa saber antes de qualquer outra.

I
Cardápio e disponibilidade juntos

Não existe endpoint separado para disponibilidade. disponivel e motivo vêm dentro de cada pizza, em /v1/menu e /v1/menu/{id}.

II
Nunca devolve 503

Se o Estoque cair dos dois lados (A e B), o cardápio ainda responde 200 — só a disponibilidade fica null, com um aviso.

III
Preço mora aqui

Decisão nossa: o Catálogo é quem já tem o dado descritivo da pizza, então o preço viaja junto — não vem do Estoque.

Base URL

Produção   https://pzaas.online/webhook/turmaa12
Teste      https://pzaas.online/webhook-test/turmaa12

A URL de teste só responde com o workflow aberto no editor, em modo Execute workflow. Para integração, use sempre a de produção.

Integração em 3 minutos

Três comandos. Se os três passarem, a integração está funcionando.

1. Confirme que estamos no ar

curl -i https://pzaas.online/webhook/turmaa12/health

Esperado: 200, "status": "ok". Este é o único endpoint sem autenticação.

2. Peça o cardápio completo

curl -s https://pzaas.online/webhook/turmaa12/v1/menu \
  -H "x-api-key: turma2026"

Repare em disponivel e motivo dentro de cada pizza — é a resposta do Estoque já embutida, sem precisar de uma segunda chamada.

3. Peça uma pizza específica

curl -s https://pzaas.online/webhook/turmaa12/v1/menu/mussarela \
  -H "x-api-key: turma2026"
Se disponivel vier sempre null. ESTOQUE_A e ESTOQUE_B (nó Config) já apontam para URLs reais — se mesmo assim vier null, é o fluxo de degradação graciosa entrando em ação porque os dois não responderam a tempo. O cardápio continua funcionando; só a disponibilidade fica em branco.

Padrões e autenticação

HeaderValorObrigatório em
x-api-keyturma2026Todos, exceto /health
  • Protocolo HTTP/JSON, versão v1 no caminho.
  • Todos os três endpoints são GET — nenhum aceita corpo.
  • x-pedido-id não se aplica: este serviço não participa do ciclo de vida do pedido.
  • Toda resposta traz servico: "catalogo-a", para identificar quem respondeu.

Arquitetura

O Catálogo é a porta de entrada do PZaaS: antes de existir pedido, pagamento ou produção, alguém precisa saber o que está à venda. Este serviço tem um trabalho só — ser a única fonte de verdade sobre o cardápio e o preço — e uma única dependência externa.

Entrada
Quem chama este serviço

API Gateway, para exibir o cardápio ao cliente final. Estoque, Pagamento ou Orquestrador, quando precisam confirmar que um pizza_id existe e qual o preço vigente.

Saída
Quem este serviço chama

Estoque A e Estoque B, com retry e fallback — embutido em toda chamada a /v1/menu e /v1/menu/{id}, nunca num endpoint à parte. E o Logger, de forma assíncrona, depois de responder ao cliente.

Por que sem banco de dados. Hoje são só dois sabores fixos — uma lista dentro do código resolve com menos peça pra quebrar, sem credencial nem conexão. O limite é claro: não escala para mais sabores. No dia em que aparecer um terceiro sabor ou uma promoção variável, a migração para Postgres (tabela turmaa12_cardapio) deixa de ser opcional.

Fluxos de chamada

Seis cenários cobrem tudo que pode acontecer numa chamada a este serviço — do caminho feliz à falha total do Estoque. Cada card é a cor do que ele representa: verde é sucesso direto, âmbar é sucesso com desvio, vermelho é erro de verdade, e o card neutro é o único caso em que "sem resposta do Estoque" não conta como falha.

200 · caminho feliz
Fluxo padrão

Webhook recebe a chamada → confere x-api-key → monta o cardápio fixo → consulta o Estoque A, que responde dentro do timeout → combina cardápio e disponibilidade → responde 200 com disponibilidade_origem: "estoque-a" → log assíncrono.

200 · +~17s
Fluxo de fallback (A → B)

O Estoque A esgota as 3 tentativas (5s de timeout, 1s de espera entre elas) sem responder → a mesma chamada, com o mesmo payload, é refeita para o Estoque B → se B responder, o cardápio sai normal, só que com disponibilidade_origem: "estoque-b".

200 · +~34s · não é erro
Fluxo de degradação graciosa

Estoque A e B falham os dois → o cardápio responde 200 assim mesmo: sabor, ingrediente e preço continuam completos, só disponivel vira null em cada pizza, com um aviso explicando o motivo. Nunca 503 — essa é a diferença central para o Orquestrador.

401
Fluxo de autenticação recusada

x-api-key ausente ou errada é verificado logo na entrada, antes de montar o cardápio ou gastar tempo chamando o Estoque. Resposta imediata, sem nenhuma dependência externa envolvida.

404 · só em /v1/menu/{id}
Fluxo de pizza não encontrada

O pizza_id não bate com nenhum sabor do cardápio fixo → responde 404 imediatamente, sem chamar o Estoque. Não faz sentido perguntar disponibilidade de um sabor que não existe.

assíncrono, depois da resposta
Fluxo de observabilidade

Todo caminho acima — sucesso, fallback, degradação ou erro — termina enviando um log estruturado ao Logger, sempre depois de já ter respondido ao cliente. Se o Logger cair, ninguém percebe: sem retry, sem bloqueio.

Não existe 503 neste serviço. Diferente do Orquestrador, uma falha do Estoque nunca impede o Catálogo de responder — ela só degrada o campo disponivel.

Resiliência

O que acontece quando a única dependência externa deste serviço — o Estoque — falha.

Camada 1
Retry

3 tentativas no Estoque A, timeout de 5s cada, 1s de espera entre elas.

Camada 2
Fallback A → B

Esgotadas as tentativas no A, a mesma chamada vai para o B — mesmo payload.

Camada 3
Degradação graciosa

Se A e B falharem os dois, o cardápio responde 200 com disponivel: null — nunca 503.

ItemValor
Tentativas por estoque3
Timeout por tentativa5s
Pior caso (A e B fora)~34s antes de degradar

Observabilidade

Todo caminho — sucesso, erro e degradação — envia log estruturado ao Logger, sempre depois de responder ao cliente.

Contrato em aberto

Pontos que ainda dependem de acordo com outras duplas — listados aqui de propósito.

Formato da resposta do Estoque. ESTOQUE_A e ESTOQUE_B já apontam para URLs reais (não são mais o placeholder de exemplo), mas a leitura da resposta continua tolerante de propósito: aceitamos disponivel, status ou item ausente, com motivo/mensagem como razão. O formato exato — e se o pizza_id bate com o que Estoque envia — ainda não foi confirmado formalmente com a dupla do Estoque.
Avisar o Pagamento. O preço mora no Catálogo, não no Estoque — ainda não comunicamos isso formalmente à dupla do Pagamento.

Não implementado por decisão de escopo: reserva de ingrediente (a consulta é só leitura), promoção real (o campo existe, vem sempre vazio), e par B do próprio Catálogo.

Resolvido. A URL do Logger já não é mais placeholder — LOGGER aponta para o serviço da dupla responsável e todo caminho (sucesso, erro, degradação) envia log estruturado depois de responder.
